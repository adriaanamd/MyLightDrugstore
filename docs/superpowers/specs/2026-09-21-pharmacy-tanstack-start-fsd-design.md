# MyLightDrugstore TanStack Start and Full FSD Refactor Design

## Goal

Refactor `MyLightDrugstore-Frontend` from a Vite React application with a localStorage mock API into a TanStack Start application organized according to the full Feature-Sliced Design structure used by `school/MeatLens/botchabuster/frontend`, while wiring every existing pharmacy workflow to the Laravel v1 API through its AES-256-GCM transport contract.

## Scope

This is a complete frontend cutover. All current pharmacy screens and workflows remain available, but their data and mutations come from `MyLightDrugstore-Backend`. The local mock database, mock API client, mock session persistence, Figma Make scaffold, and Figma-only assets/configuration are removed.

The existing backend endpoints and response contracts in `API-DOCS.md` are the source of truth. Backend business behavior is not reimplemented in TanStack Start.

## Reference architecture

The frontend will follow the structure and boundary conventions observed in:

- `school/MeatLens/botchabuster/frontend-structure-plan.md`
- `school/MeatLens/botchabuster/frontend/scripts/check-fsd-boundaries.mjs`
- `school/MeatLens/botchabuster/frontend/src`

The layer dependency direction is:

```text
shared <- entities <- features <- widgets <- pages <- app
```

The implementation will preserve Botchabuster's conventions:

- `api`, `model`, `lib`, and `ui` subdirectories are created inside slices where they provide a clear boundary.
- Slice `index.ts` files are the public APIs for cross-slice imports.
- Deep imports across slices are forbidden.
- Generic UI and utilities belong in `shared`, domain models and public entity behavior in `entities`, user workflows in `features`, page-sized compositions in `widgets`, and route-level screens in `pages`.
- Automated FSD boundary and source-size checks are part of the frontend quality gate.

Botchabuster uses Vite with React Router. This project will retain the same FSD boundaries while adapting the routing layer to TanStack Start's file-based routes.

## TanStack Start integration

TanStack Start will provide the application runtime, file-based route discovery, router creation, and server entry. The route tree will be generated by TanStack's tooling and will not contain business logic.

The intended source layout is:

```text
MyLightDrugstore-Frontend/
  src/
    app/
      providers/
      router/
      styles/
    routes/
      __root.tsx
      login.tsx
      _authenticated.tsx
      _authenticated/
        dashboard.tsx
        catalog/medicines.tsx
        inventory/index.tsx
        inventory/receipts.tsx
        inventory/adjustments.tsx
        inventory/movements.tsx
        sales/index.tsx
        sales/new.tsx
        sales/cart.tsx
        sales/print/$saleId.tsx
        reports/inventory.tsx
        reports/sales.tsx
        settings/security.tsx
        admin/users.tsx
        backups.tsx
    pages/
    widgets/
    features/
    entities/
    shared/
    routeTree.gen.ts
    client.tsx
    server.ts
```

Route files are thin adapters. They apply route-level auth or admin guards, define search/path parameters and loaders, and render the corresponding `pages` component. The print route uses the `$saleId` path parameter. Dashboard, table, report, and form filters use typed TanStack Router search parameters so they survive refreshes and can be shared by URL.

The root route provides global error handling, document metadata, and the application providers. The authenticated layout renders the FSD app shell and an outlet. The Start server entry is limited to Start request handling; it does not proxy Laravel business operations or contain a second copy of the domain model.

## FSD slice responsibilities

### `app`

Application composition, TanStack Start entry points, providers, query client setup, authenticated/admin route guards, session bootstrap, and global styles.

### `pages`

Route-level screens for login, dashboard, catalog, inventory, sales, reports, security, staff users, backups, and sale printing. Pages compose widgets and features but do not own transport details or domain mutation rules.

### `widgets`

The application shell/navigation, dashboard overview sections, inventory and sales tables, report sections, and other larger reusable screen compositions.

### `features`

User-facing workflows including login/logout, medicine create/edit/archive, receiving stock, inventory adjustments, sale creation, cart line actions, mark-paid/cancel flows, password change, staff administration, and backup request/download.

### `entities`

Client-safe domain models, response mappers, query keys, and entity-level UI primitives for users/sessions, medicines, inventory lots and movements, sales, reports, and backup jobs.

### `shared`

The encrypted HTTP transport, API error normalization, request ID generation, environment/configuration, generic UI primitives, date/money formatting, storage utilities that do not contain session credentials, and generic hooks/utilities.

## Backend data flow

The application data path is:

```text
TanStack route loader or TanStack Query
  -> entity/feature API adapter
  -> shared encrypted transport
  -> Laravel /api/v1 endpoint
```

The frontend uses Laravel-managed HTTP-only session cookies. `credentials: include` is required for API requests. Session credentials are never stored in localStorage, sessionStorage, URL parameters, or application state that is persisted to disk.

The public-key bootstrap endpoint is requested in plaintext. For every other API request, the shared transport:

1. Reads or refreshes the current public transport key metadata.
2. Generates a fresh 32-byte AES key.
3. Wraps that AES key with the advertised RSA public key using RSA-OAEP with SHA-256.
4. Sends `X-Transport-Key` as `<keyId>.<base64url-wrapped-key>`.
5. Serializes JSON requests as the documented transport descriptor.
6. Encrypts the descriptor with AES-256-GCM using a fresh 12-byte nonce.
7. Uses the uppercase method, one space, and normalized path without query string as AES-GCM additional authenticated data.
8. Decrypts the response descriptor, reconstructs UTF-8 or binary response bodies, and preserves HTTP status and safe response headers.

The client must support JSON responses, bodyless requests, and encrypted binary downloads for backup artifacts. It must use canonical base64url handling and reject malformed envelopes, invalid nonce/tag lengths, unsupported algorithms, and authentication failures without logging keys, decrypted bodies, or sensitive response data.

CSRF state is obtained from `GET /auth/csrf` after transport bootstrap and is retained in memory. Mutating requests send `X-CSRF-TOKEN`. A `419` response may refresh CSRF state and retry the mutation once. Sale creation, sale-item addition, and stock receipts use a generated idempotency key and never silently retry with a new key.

TanStack Query owns server-state caching. Query keys are defined by entity or feature public APIs. Successful mutations invalidate the smallest affected query groups, including related dashboard, inventory, sales, report, and detail queries where necessary.

## Route and workflow coverage

The migration preserves these route-level workflows:

- Login and authenticated session bootstrap.
- Dashboard inventory/sales overview.
- Medicine catalog search, create, edit, stock receipt, and archive.
- Inventory overview, receipts, adjustments, lots, and movement history.
- New sales, open cart, sale history, print view, mark-paid, line removal, and cancellation.
- Inventory and sales reports.
- Current-user password change.
- Admin staff-account list/create/update/deactivate.
- Backup request and admin-only status/download.
- Server-time display in the application shell.

The frontend maps these workflows to the documented `/api/v1` endpoints. It does not preserve the mock API's localStorage behavior and does not send client-computed stock totals, prices, or sale totals where the backend is authoritative.

## Error and permission behavior

The normalized API error shape retains `code`, `message`, optional field `details`, and `requestId`.

- `401`: clear the in-memory session and navigate to login.
- `403`: render an explicit permission state and keep the protected data unavailable.
- `419`: refresh CSRF state once and retry the mutation once; then surface a safe error.
- `409`: show a state-conflict message and preserve the current form/cart state.
- `422`: map field details to the owning feature form and show the safe server message.
- `5xx` or transport authentication errors: show safe retry guidance and the request ID without exposing cryptographic or decrypted data.

Admin-only pages are guarded both in navigation visibility and in the route guard. The backend remains the authority for authorization.

## Figma removal

The frontend cutover deletes every Figma-specific trace in the frontend project:

- `.figma/` scripts and site metadata.
- Figma plugins and custom Vite hooks.
- `FIGMA_*` environment variables and Figma-only URL/configuration behavior.
- Figma placeholder comments and metadata slots in `index.html`.
- Figma package names and documentation wording.
- Figma-only assets or pasted imports that are not application resources.

The replacement `index.html`, package metadata, instructions, and Vite/TanStack configuration use ordinary MyLightDrugstore application naming and behavior.

## Testing and quality gates

The frontend will add or retain checks for:

- FSD boundary violations and legacy root ownership.
- Source-size limits for production files.
- TypeScript type correctness.
- Formatting and linting.
- Production TanStack Start build.
- Transport crypto and envelope behavior.
- API response/error mapping and query invalidation.
- Auth/admin route guards.
- Feature workflows for catalog, inventory, sales, reports, users, security, backups, and print/download behavior.

The repository's backend CI remains blocking and unchanged. Frontend CI will run its lockfile-based install plus architecture, typecheck, lint/format, test, and production build commands. No existing backend tests or required quality gates will be weakened, skipped, or made advisory.

## Acceptance criteria

The refactor is complete when:

1. The frontend starts and builds as a TanStack Start application.
2. All current pharmacy routes are available through TanStack file-based routing.
3. All data reads and mutations use the Laravel v1 API through the documented AES-256-GCM transport.
4. No localStorage mock database, mock API calls, or mock session credentials remain.
5. The full FSD layer/slice structure matches the Botchabuster pattern and boundary checks pass.
6. Login, authorization, catalog, inventory, sales, reports, users, security, backup, server time, and print/download flows are covered by tests appropriate to their risk.
7. `rg -i "figma"` finds no Figma-specific trace in the frontend project, excluding unrelated historical documentation outside the frontend scope.
8. Fresh local verification output shows the frontend quality gates and the applicable backend CI gates passing.
